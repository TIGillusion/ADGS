# ADGS 交互增强：打断 CEO / 终止下层 / 任务队列（设计文档）

## 需求回顾
1. 任务执行中，用户可以直接给 CEO 发消息（打断当前 CEO 循环），**不打断正在执行的子节点**
2. CEO / 任何上层节点有权**终止 / 打断下层节点**的任务
3. `/queue` 指令：当前任务执行完，自动提交提前设置好的下一个对话

---

## 现状基础（已查证）

| 能力 | 现状 |
|---|---|
| CEO talk 循环 | `while step < limit` 单线程，`ask_user` 时返回挂起（`_task_done=False`），用户回答走 `/api/chat` 再次 `talk()` 接着上下文 |
| /api/chat | `_busy["state"]` 为 True 时**直接拒绝**（"已有任务正在执行"） |
| ask_user 挂起 | CEO 提问后 talk 返回，`_busy` 解锁？→ 需确认：`ask_user` 返回后 runner 的 finally 会 `_busy=False`，所以提问时能回答 ✓ |
| 节点 hermes 进程 | `core/hermes.py` 里 Popen，但**进程句柄是局部变量**，无全局注册表 |
| 委派链 | `_delegate` 用 ThreadPoolExecutor 派发，子节点 work() 阻塞等待 |

---

## 设计

### 功能一：打断 CEO（插话），不打断子节点

**核心思路**：把 CEO 的"等待子节点结果"从阻塞式改为**可中断式**——talk 循环每步检查"是否有用户插话"，有则注入为 system 消息让 CEO 决策（继续等 / 调整 / 停止）。

**现状问题**：`_dispatch_step` 是**同步阻塞**的（`NODE.work()` 一直等到子节点完成），期间 CEO 线程卡死，无法响应插话。

**改动方案**（core/ceo.py）：
```
1. 新增 self._pending_msg = None  # 用户插话缓冲（web 线程写入）
2. talk() 主循环每步开头检查：
   if self._pending_msg:
       msg = self._pending_msg; self._pending_msg = None
       history.append({"role":"user","content": f"【用户插话】{msg}"})
       bus.emit("chat.user_interrupt", text=msg)
       # 不重置循环，CEO 看到插话后自行决策
3. 新增方法 inject_message(text): self._pending_msg = text
   （web 调用，不阻塞）
4. _dispatch_step 的阻塞等待改造（关键）：
   - work() 调用改到子线程，主循环轮询结果 + 检查插话
   - 或：保持阻塞，但插话只在下一次 talk 时生效（简化版）
```

**简化版（推荐先做）**：插话不打断进行中的 `_dispatch_step` 阻塞，但：
- 用户插话 → 存 `_pending_msg` → 返回"已接收，当前子任务完成后 CEO 会看到"
- 当前派发返回后，talk 循环下一步读到插话并处理
- 子节点全程不受影响 ✓（它们本来就是独立进程）

**效果**：任务中任何时刻发消息 → 前端显示"已接收" → 当前子任务完成后 CEO 收到插话，可决定追加需求/调整方向/提前收尾。不打断子节点 ✓

### 功能二：上层终止下层节点

**核心思路**：进程注册表（全局 dict：node_id → 活跃 hermes Popen）+ 终止 API。

**改动方案**：
```
1. core/hermes.py：
   - 新增全局 _ACTIVE_PROCS = {}（threading.Lock 保护）
   - execute()/resume() Popen 后注册：_ACTIVE_PROCS[profile] = proc
   - 进程结束 finally 里注销
   - 新增静态方法 kill_active(profile) -> bool：找到 proc.kill()
2. core/node.py：
   - NODE 类加 abort()：调 HermesInstance.kill_active(self.profile)
   - _delegate 等待子节点时，若收到上层 abort 信号 → 终止所有活跃子进程
3. core/ceo.py：
   - CEO 加 abort_node(node_id)：调 NODE(node_id).abort()
   - 新增工具 abort_task（给 CEO 的 tool）：参数 node_id
4. web_app.py：
   - POST /api/abort {node_id} → 终止该节点（及它委派的下层？）
   - 终止语义：kill 该节点的 hermes 进程 → work() 返回 exit!=0 → 上层感知失败
5. 委派链传递：上层 abort 时，向所有子节点广播（遍历 registry/委派记录）
```

**终止粒度**：
- 单节点：kill 该节点 hermes 进程
- 递归：abort 该节点 + 它 spawn 的所有子节点（用 _delegate 的 children 记录递归 kill）

**前端**：节点详情加"终止"按钮（delegating/running 状态可点）→ POST /api/abort

### 功能三：/queue 任务队列

**核心思路**：web_app 加内存队列，当前任务结束自动提交下一个。

**改动方案**：
```
1. web_app.py：
   - 新增 _queue = []（+ lock）
   - POST /api/queue {text} → 追加到队列，返回"已加入队列（第 N 位）"
   - runner() finally 里：_busy=False 后，若 _queue 非空 → pop 下一个自动提交
     （复用 api_chat 的 runner 逻辑）
   - 前端指令 /queue 显示队列状态，/queue clear 清空
2. 自动提交循环：
   - finally: _busy=False; emit 任务结束
   - if _queue: text = _queue.pop(0); _busy=True; 启动 runner(text)
   - 队列空则停
3. 前端（app.js）：
   - 指令 /queue 走 /api/command 分支（显示队列）
   - 新指令 /queue add <text> 或直接复用 /api/queue
   - 状态栏显示队列长度
```

**队列与插话关系**：/queue 是"串行队列"（一个做完做下一个）；插话是"当前任务中注入消息"。两者独立。

## 风险与注意
- **插话时机**：CEO 在 `_dispatch_step` 阻塞时插话不会立即生效（等当前派发返回）——需前端提示"已接收，子任务完成后生效"
- **终止的连锁反应**：kill 节点 hermes → work() 非零退出 → 上层把该子任务标记失败 → CEO 可能重派（或整任务失败）——终止语义要明确（预期行为）
- **队列与 ask_user**：队列自动提交遇到 CEO 提问时，应暂停等用户回答（不能自动替用户答）——runner 需检测 ask_user 挂起

## 实施顺序
1. 功能二（终止下层）：进程注册表最基础，先做，风险低
2. 功能一（打断 CEO）：依赖 talk 循环改造，中等
3. 功能三（/queue）：web 层独立，最后做
