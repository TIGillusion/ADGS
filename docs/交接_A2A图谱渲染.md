## 五、关键技术事实(接手必读)

1. **架构**:`web_app.py` 只是壳,/api 全部代理给长驻 `runtime_host`(host.json 记 pid)。**改后端代码必须杀 runtime_host 进程**;前端改动只需重新 `npm run build` + 浏览器强刷。
2. **并发会话**:有另一个 AI 会话在同时修改 ADGS(后端+前端),文件随时可能变化。改文件前先读当前内容;**禁止 git add -A**;git 长期不提交是团队约定。
3. **事件管线**:SSE `/api/events` → store.handleEvent → (会话过滤 → 聊天消息 → GRAPH_RELEVANT 集合的图事件进 applyEventToGraph → recordExecutionEvent 归档)。A2A 事件:`a2a.delegate`(委派/汇报)、`a2a.verdict`(复核),`data.delegation_id` 关联。
4. **树模型**:图谱是严格的 CEO → round-N → task → `node@execution` 树;A2A 委派的对方不在树里 → 虚拟锚点(A2aEdge 端点);A2A 子执行的 `task_id` 以 `mesh_` 开头,被 reducer 显式排除在树外。
5. **测试**:`cd web3 && npx vitest run`(156 项);`npx tsc --noEmit`;`npm run build`。后端 `python -m pytest tests/test_mesh_a2a.py tests/test_console_log.py`。
6. **目检钩子**:`window.__adgs_store`(main.tsx)——`handleEvent(合成事件)` 可直接驱动页面;**注入的数据只在页面内存,刷新即清,但一定要带「【目检演示】」前缀并在结束后刷新**,否则用户会误认为真实数据(本次已踩坑)。
7. **用户正在使用的任务不要打断**:重启 runtime_host / 杀进程前必须确认 `busy=false`。

### 7.6 流程性问题(比代码更重要的教训)

1. **验证方法错误**:始终用合成场景验证,从未先复现用户实际画面。正确顺序应是:用户截图/描述 → 在用户环境重现 → 定位 → 修 → 用户确认。
2. **对"通过"的定义过宽**:tsc+单测+一张截图=「验证通过」——单测不覆盖视觉渲染,截图分辨率不足以暴露碰撞/重叠。
3. **多轮"声称修好"消耗了信任**:每次都应明确"我验证了什么、没验证什么",而不是笼统的"已修复,目检通过"。
4. **并发会话风险下的时序**:多次 Edit 因文件被并发修改而失败/回写丢失(ToolMsg 的换行字面量反复修了三次),最终状态的完整性需要接手者重新确认。
