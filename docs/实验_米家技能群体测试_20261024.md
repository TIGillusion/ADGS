# 实验：让 ADGS 种群整体掌握米家设备控制技能（2026-10-24）

## 目的

1. 给种群一个**通用**的米家(Mi Home)设备控制技能，验证整体掌握能力；
2. 观察任务分配是否出现**固定团体垄断**；
3. 观察是否出现**什么都自己干**或其他不良现象。

## 实验环境

- **技能**：`skills/mijia-home/`（SKILL.md + mijia.py + mijia_config.json）
  - 纯标准库实现小米云三步登录（serviceLogin → serviceLoginAuth2 → serviceToken）+ 签名请求（HMAC-SHA256）
  - 通用协议：`device_list` 发现 + `deviceapi` miSpec 读/写 + `devicecmd` 旧协议 + `api` 逃生舱；设备无关（siid/piid 探测方法论写进技能文档）
  - 登录会话缓存 `mijia_session.json`（防真实服务登录限流；MIJIA_NO_CACHE=1 绕过）
- **仿真服务**：`tests/mijia_mock_server.py`（端口 18963，状态 `data/mijia_mock/state.json`，请求日志 `data/mijia_mock/server.log` 作为地面真值）
  - 设备：测试插座 cuco.plug.cp1md（电源 2.1 / 功率 2.2 / 温度 3.1）+ 客厅人体存在传感器 lumi.presence.acn001（presence 2.1 / 照度 2.2 / 无人秒 3.1）
  - 完整鉴权（cookie + 签名字段，缺一 401）、未知属性返回 -1001、类型错误 -1002
- **播种**：技能包装进 3 个不同部族的节点 profile（ags_578 工程 / ags_441 标准库 / ags_594 白板）
- **基线快照**：`data/mijia_mock/baseline_registry.json`

## 现象观察（用户三大问题）

### 1. 固定团体任务分配？——有集中趋势，未形成垄断

- 6 任务 4 个执行者：606×3、567×1、578×1、623×1。
- 路由得分复现（当前种群）：所有任务 top-5 得分挤在 0.25~0.40，softmax(T=0.3) 后采样概率几乎均匀（各约 0.2）→ **实质是"模糊前五轮盘"，不是专家定向**。
- 历史垄断者 ags_377（98 任务/约 43% 存量）在六次复现中仅入围一次——explore_beta(0.15)+sim^1.5 改造后垄断被打破。
- **真正的"部族克隆"在描述层**：重组繁衍的新生儿描述=父代原文照抄（ags_627←606、ags_623←538 均为逐字复制），基线中大量"通用智能体节点…"完全相同的描述就是这么做出来的；克隆部族挤占 top-5 候选席，稀释了路由分辨力。
- 描述吸收闭环工作正常：4 个执行者干完都把米家能力写进了自述。

### 2. 什么都自己干？——未发现

- CEO 无执行类工具（物理上干不了活），六次均正确单任务派发；
- worker 层 a2a 纪律（"自己能高效完成的不要外派"）生效，小任务自执行是正确行为，非病态独揽；
- 无过度拆分、无重复派发、无循环决策。

### 3. 其他发现（值得注意）

- **描述与技能脱钩**：ags_606 的米家知识存在描述/会话记忆里，从未 skill_manage 固化（只读任务被任务书纪律禁止固化——守规矩的副作用）；其子代 627/623 继承了"会米家"的描述却没有技能包。知识有两条通道：任务书路径(随任务传播) > profile 技能包(可遗传) > 描述宣称(不可执行)。
- **路由不看技能包**：路由只匹配 describe。ags_626 持有技能包但描述不含米家 → 不会被定向选中。
- **诚实纪律表现优秀**：T4 功率 0.0W 标注"（推断）"、T5 注明执行者、未知属性如实记录 -1001 排除。
- 效率：改进前每次 CLI 调用都全量登录（56 次），已加会话缓存（复测 4 次调用 0 次登录）。

## 第三阶段：三项结构性修复 + T11 实证（2026-10-24 中午）

针对第二阶段发现的三个问题逐一修复（用户逐条确认方向）：

### 修复 1：技能固化恢复为节点固有权限

- **根因**：merged 改造时 `render_task_md` 技能固化段写成"仅在原始权限允许修改当前
  AGS 技能时固化"——CEO 给的 permissions 只描述工作区，worker 一对照就把自己的
  技能目录判为只读（T7 ags_538 原话）。旧模式（agent.py skill_note）本是"直接创建，
  无需确认"。
- **修复**（config/prompts.py）：改写为"技能固化是每个节点的固有权限，不需要任务权限
  授权；写入的是你自己 profile 的技能目录，不属于任务工作区、不受写路径约束；
  有可复用经验就应当固化，无人值守环境直接创建无需确认"。

### 修复 2：外部资源互斥（shared_resources）

- **根因**：调度只认工作区文件写路径，两台并行子任务操作同一台物理设备会打架
  （T7 两节点各自"先开后关"同一插座，时间上侥幸错开）。
- **修复**：
  - `core/scheduling.py` 新增 `external_resources()`：`shared_resources` 声明规范化
    为 `ext:<名>` 参与冲突判定（同名互斥）；
  - CEO 调度循环（ceo.py:1041）与 dependency_results 都并入该集合；
  - CEO/AGENT 的 split_tasks schema 加 `shared_resources` 字段 + CEO 系统提示词
    "会操作同一外部资源的子任务必须声明相同资源名，调度自动串行化"；
  - A2A 路径：`delegate_to_node` 工具加 `shared_resources` 参数，`_mesh_delegate_impl`
    对同父进行中的委派做资源互斥检查，冲突直接拒绝（强制 wait 后再发）；
  - a2a 纪律加"外部资源互斥"条目（附 T7 实测教训）。

### 修复 3：验收权回收（自评≠验收）

用户指出"想简单了"——深层问题不是推断标签宽严，而是 merged 改造把 AGENT 验收层
整个绕过后，depth=0 任务变成"自己给自己打分"，半成品也能 passed（T9 实证）。
- **修复**（core/node.py `_work_merged` + `_independent_acceptance`）：
  1. worker 自评降级为**申报**（self_reported 字段留档）；
  2. **独立验收官**：复用旧模式的 `AGENT.evaluate`（答题卡 accept_report、逐条判定、
     分块、协议修复、old+raw×delta 打分）对照任务书验收；
  3. **机械核验**托底：交付物清单里形似路径的项逐一检查存在性，结果作为证据喂给
     验收官；
  4. outcome/分数以验收官为准；申报 passed 但验收不通过 → failed 并标注
     "⚠申报与验收不一致"；验收官不可用 → unjudged（不再按产出推断 passed）；
  5. A2A 子执行仍保留父复核二次修正（双层验收）。

## 第四阶段：分层验收体系（2026-10-24 下午，用户设计）

用户定义的完整模型：**打分权 = 直系上级**（谁派活谁打分）；worker 自评只是申报；
验证优先外包给专门节点（形成可进化的验证生态位）；越级纠错是例外权（可扣可加，须附
证据）；中断/没报告不推断成败而是自动注入确认；所有打分幅度受限；A2A 记录全部留档、
产物集中归置。

### 实现

| 机制 | 落点 |
|---|---|
| 任务终结保障 | node.py `_work_merged`：无申报/报告不完整 → 自动 resume 注入「终结确认」（继续/完成报告/放弃报告三选一，最多 2 次），仍无终结 → unjudged（彻底删除"≥200字推断 passed"）|
| 直系上级打分（mesh 链） | `report_delegation_verdict` 加 score 参数（-10~+10 粒度），×delta_coef 修正子分（T13 实测 worker 打出 score=+7 并附扣分理由）|
| CEO 直系结算 | ceo.py `_settle_direct_reports`：finish 时账本结论程序化映射（passed→+2 / failed→-2 / 其它 0，每任务一次），事件 ceo.settle 留档 |
| 越级纠错（可扣可加） | 新 MCP 工具 `escalate_delegation_verdict`：须附证据（note≥10字）、系统校验"调用者确是委派父的直系上级"（执行存档 upper 链），幅度同限制，a2a.escalate 留档 |
| 验证外包 + 打分指引 | a2a 纪律第 5/6 条：核验优先委派未参与节点；所有下属完毕后综合汇报用 score 逐一直系打分 |
| 委派档案持久化 | `.adgs_runtime/mesh_delegations.json`（delegate/verdict/escalate/结束均落盘，runtime 启动恢复）|
| 产物归置 | `<workspace>/.adgs_artifacts/<run_id>/`：报告/日志/交接文档统一（scheduling.artifact_dir + 任务书「产物归置」段 + 产物目录写授权豁免——只读任务的报告也落盘）|

### 实测（T12/T13）与中途抓到的三个缺陷

行为面全部验证：ags_623 主任务 → probe 选出有验证能力的 ags_567 → 委派独立复核
（shared_resources 声明两台设备）→ verdict score=+7（扣 3 分因"汇报未逐字附原始 JSON"
——真实质量区分）；CEO 拆两路时各自带验证节点（ags_578/ags_606），其中一路 score=2；
产物归置生效（.adgs_artifacts/<run_id>/）；CEO 发现账本有历史 unjudged 记录时**如实
finish=blocked 而非硬报完成**。

缺陷与修复：
1. **__pycache__ 陈旧缓存**：runtime 混跑新旧代码（ceo.settle 有、verdict score 无、
   档案不落盘）——清 __pycache__ 后恢复（README 踩坑 8 再度验证）；
2. **frozenset 不可 JSON 序列化**：委派档案写盘静默失败 → 记录改存 sorted list；
3. **验收官旧规则误伤**：`passed=True + failed_items → 打回` 把"总体通过、带非阻断
   瑕疵"的正常判定打成协议失败（T13 首轮 protocol_error 实证）→ 语义反转：合法；
   仅 `passed=False 且无 failed_items`（失败却无依据）才打回；验收官自身故障的
   执行 state 统一标 unjudged（不再标 protocol_error 误导）。

测试：merged 终结保障 3 用例（确认后交报告 / 两次确认仍无 → unjudged）+ 验收官
语义 2 用例（带瑕疵通过一次过 / 失败无依据才打回），96 passed。
